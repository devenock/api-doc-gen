api-doc-gen

Scan your Go API and generate Swagger/OpenAPI or a Postman Collection — no annotations, no code changes. Supports Gin, Echo, Fiber, Gorilla Mux, and Chi.

$ go install github.com/devenock/api-doc-gen@latest

Why

The standard way to generate OpenAPI docs for a Go API — swaggo/swag — works by parsing comment annotations you write above every handler:

// @Summary      Show an account
// @Router       /accounts/{id} [get]
// @Param        id   path  int  true  "Account ID"
// @Success      200  {object}  model.Account
func (c *Controller) ShowAccount(ctx *gin.Context) {

That's a real, well-established tool, but the annotations are a second source of truth you maintain by hand: add an endpoint and forget the comment block, and the docs silently fall behind the code with no error to catch it.

api-doc-gen removes that step entirely. It reads your code as-is — route registrations, handler signatures, request/response structs, binding calls — via Go's own AST parser, the same way go vet or gofmt do, and builds the OpenAPI/Postman spec from what's actually there. No comments to write, no existing code to touch.

One consequence of that: because there's nothing to keep in sync, docs stay accurate as you build incrementally. Register one handler, generate, ship; add the next one whenever it's ready, generate again — each run reflects exactly what's in the code at that moment, with zero extra steps. (To be precise: every run is a full, fresh scan of the project, not a cached diff of what changed — "incremental" describes the workflow this enables, not an incremental-build engine under the hood.)

"No annotations" only helps if the scanner is actually reliable, so the analyzer is built to degrade honestly rather than guess silently: it resolves route groups, auth middleware, embedded struct fields, query/path parameters, and response bodies across real-world patterns in Gin, Echo, Fiber, Gorilla Mux, and Chi; falls back to generic net/http-style detection for anything else; and surfaces ambiguity instead of hiding it — a .go file that fails to parse, a framework it can't confidently pick between, or zero endpoints found are all reported explicitly (-v for detail) rather than producing a spec that looks complete but silently isn't.

Install

Requires Go 1.26.8+. The binary is installed to $(go env GOPATH)/bin — usually ~/go/bin. Make sure that directory is on your PATH.

# Add to ~/.zshrc or ~/.bashrc if needed
export PATH="$PATH:$(go env GOPATH)/bin"

Verify:

api-doc-gen --version
No Go toolchain? Prebuilt binaries for Linux, macOS, and Windows (amd64/arm64) are published on the Releases page for every tagged version.

Generate docs

Run from your Go project root — the directory that contains go.mod and your route definitions.

# Interactive wizard — choose type, output dir, title, etc.
api-doc-gen generate

# Or non-interactive — skip all prompts
api-doc-gen generate --no-interactive --type swagger -o ./docs
api-doc-gen generate --no-interactive --type postman -o ./docs

Point at a project in a different directory:

api-doc-gen generate /path/to/your-api --no-interactive --type swagger -o /path/to/your-api/docs
Run api-doc-gen init inside your project to generate a .apidoc-gen.yaml config file. Commit it so the whole team shares the same defaults.

Output

TypeFiles
swagger openapi.json · openapi.yaml · index.html (Swagger UI)
postman collection.json (Postman Collection v2.1)

Swagger — after generating, a local preview server starts automatically (bound to 127.0.0.1 only — never exposed to your network) and opens index.html in your browser. Pass -q/--quiet in CI or scripts to skip this. The Swagger UI assets are vendored into the binary and written alongside your docs, so the page works fully offline — no CDN calls, nothing to break if you view it later without a network connection. To reopen it later, open ./docs/index.html directly in your browser.

Postman — open Postman, click Import in the sidebar, and drag collection.json onto the dialog. Endpoints are organized into folders by tag, with example request bodies and bearer auth pre-wired.

Coverage

What the analyzer actually detects and emits, checked against the code rather than aspirational.

Supported

  • Paths, operations, path and query parameters
  • Request bodies — JSON binding calls (ShouldBindJSON, BodyParser, Decode, and common project-specific wrapper names matched by hint)
  • Response bodies — JSON responses across Gin/Echo/Fiber/Gorilla Mux/Chi/net/http response patterns
  • Bearer auth detection — marks a route security: [BearerAuth] when its middleware looks like auth (or matches your configured auth_middleware list)
  • Struct tags — json (name, omitempty, - to exclude), binding:"required" / validate:"required"
  • Embedded struct fields promoted into the parent schema
  • Tags for Swagger UI grouping, derived from the path
  • OpenAPI 3.0.3 and Postman Collection v2.1 output
  • Common external types — time.Time, time.Duration, uuid.UUID (google/uuid), and database/sql's Null* types resolve to their real, verified JSON shape (checked against encoding/json's actual output, not assumed — sql.NullString looks like it should marshal as a plain string, but it has no custom MarshalJSON, so it's really {"String":...,"Valid":...})

Not yet supported

  • Header parameters — not extracted
  • Non-JSON content types — request/response bodies are always modeled as application/json; no multipart/form-data, XML, or plain text
  • Auth schemes other than Bearer — no API Key, Basic Auth, or OAuth2 security scheme detection
  • Enums, example values, response headers — the schema model has fields for all three (so output stays forward-compatible), but nothing in the analyzer populates them yet
  • Any other type from outside the scanned project (a third-party library type not in the supported list above, a shared internal module, etc.) resolves to an empty object with no fields
  • File uploads (multipart/form-data) — not detected

Found a pattern that isn't covered? Open an issue — new patterns belong in the analyzer, not worked around.

Applying it to your project

Your project does not need any changes — the tool reads your existing route definitions.

Recommended layout

my-go-api/
├── go.mod
├── main.go
├── handlers/
├── .apidoc-gen.yaml   ← optional config (see below)
└── docs/              ← generated output

Optional Makefile target

So the whole team runs the same command:

docs:
	api-doc-gen generate --no-interactive --type swagger -o ./docs

Optional config file

Run api-doc-gen init inside your project to create .apidoc-gen.yaml. Commit it so everyone shares the same defaults (output dir, title, framework, etc.). In interactive mode, doc type and framework are skipped entirely once set in the file; title, version, base path, and output directory are still prompted but pre-filled with the file's value — press Enter to accept it. Use --no-interactive to skip all prompts and use the file (plus flags/env) as-is.

Config file

Create .apidoc-gen.yaml in your project root to set persistent defaults. Run api-doc-gen init to generate one interactively.

# .apidoc-gen.yaml
type: swagger
output: ./docs
framework: ""       # leave blank to auto-detect from go.mod
title: My API
version: 1.0.0

Precedence

Configuration is merged from lowest to highest precedence — flags always win:

  1. Config file — .apidoc-gen.yaml in the current directory (or the path set by --config)
  2. Env vars — APIDOC_<KEY> (e.g. APIDOC_TYPE, APIDOC_OUTPUT)
  3. Flags — e.g. --type swagger, -o ./docs

Auth middleware detection

Config-file only (no flag/env equivalent). By default, a route group is marked authenticated (security: [BearerAuth] in the generated spec) when its middleware's name contains auth or jwt (case-insensitive), plus a small set of common exact names. Set auth_middleware in .apidoc-gen.yaml to override that heuristic entirely with an exact (case-insensitive) list of your own middleware names:

auth_middleware:
  - requireSession
  - JWTAuth

Run with -v to see exactly what was matched, either way.

Postman API key resolution

The Postman API key is never stored in .apidoc-gen.yaml. Resolution order:

  1. --postman-api-key <key>
  2. APIDOC_POSTMAN_API_KEY
  3. POSTMAN_API_KEY
  4. ~/.config/apidoc-gen/credentials.json (written on first interactive prompt; mode 0600)
  5. Interactive prompt (only when --no-interactive is not set)

Build check

Before analyzing, generate runs go vet ./... against the target project as a pre-flight check. It's purely advisory — a project that fails it still gets docs generated from whatever the AST parser can recover, but you get a warning up front that the result may be incomplete, rather than silently missing routes with no explanation:

⚠️  This project does not currently pass `go vet ./...` —
   generated docs may be incomplete or incorrect.
   Run with -v for details, or pass --skip-build-check to suppress this check.

Pass --skip-build-check to disable it (e.g. running against a branch mid-refactor in CI). It also skips itself automatically wherever the go toolchain isn't on PATH — including this project's own Docker runtime image, which ships as a slim alpine base with just the compiled binary and no Go toolchain.

Postman

Manual import (default)

Generate collection.json, then in Postman click Import in the sidebar and drag the file onto the dialog.

Auto-upload

Pass --upload to have the CLI upload the collection directly to your Postman workspace via the Postman API. You'll be prompted for an API key the first time; generate one at postman.co/settings/me/api-keys. The key is saved to ~/.config/apidoc-gen/credentials.json and reused on future runs. Repeat runs update the same collection — no duplicates.

# First run — prompts for key once, then uploads
api-doc-gen generate --no-interactive --type postman --upload -o ./docs

# CI — read key from env, fail loudly if missing
APIDOC_POSTMAN_API_KEY=your_key api-doc-gen generate -y --type postman --upload

# Generate file only, skip upload entirely
api-doc-gen generate -y --type postman --no-upload

The collection UID is cached in .apidoc-gen-cache.json (gitignored) so subsequent uploads always update the same collection. See the upload behaviour matrix for exactly what happens in each mode.

Docker

No Go installation needed. Pull the published image:

docker run --rm \
  -v "$(pwd)":/workspace \
  -w /workspace \
  ghcr.io/devenock/api-doc-gen:latest generate --no-interactive --type swagger -o ./docs

Or build it yourself from source:

docker build -t api-doc-gen .

docker run --rm \
  -v "$(pwd)":/workspace \
  -w /workspace \
  api-doc-gen generate --no-interactive --type swagger -o ./docs

Replace $(pwd) with the path to your API project if you're not running from its root. The container runs as a non-root user — if generated files come out owned by a UID your host user can't write to, add --user "$(id -u):$(id -g)" to the docker run command.

CI & scripts

Always pass -y and --type so the CLI never waits for input.

# GitHub Actions example
- name: Generate API docs
  run: |
    go install github.com/devenock/api-doc-gen@latest
    api-doc-gen generate -y --type swagger -o ./docs --title "My API"

Exit codes: 0 success · 1 validation error · 2 runtime error.

Security

api-doc-gen only reads your project's source to extract routes and types via static AST parsing — it never executes your code. A few specific hardening notes, since this runs against real codebases:

  • Confined file access — every file read is scoped to your project directory via Go's os.Root, so a symlink (accidental or crafted) pointing outside the project tree is never followed, even if it's swapped in mid-scan.
  • Output stays put — the output directory is validated to stay within your working directory unless you pass --output/-o explicitly yourself, so a .apidoc-gen.yaml from a repo you don't control can't silently redirect where files get written.
  • Local-only preview — the Swagger UI preview server binds to 127.0.0.1, never your network, and generated docs are fully offline (no CDN dependency).
  • Secrets stay out of it — the Postman API key is never written to .apidoc-gen.yaml; it's stored at ~/.config/apidoc-gen/credentials.json with 0600 permissions.

Found a security issue? See SECURITY.md for how to report it.

Troubleshooting

Command not found after go install

Go's bin directory is not on your PATH. Add it and reload your shell:

export PATH="$PATH:$(go env GOPATH)/bin"
source ~/.zshrc   # or ~/.bashrc

No endpoints found

Usually one of:

  • The framework wasn't auto-detected — pass --framework explicitly (e.g. --framework gin).
  • Routes are registered in a file inside an excluded directory (vendor, test, tests, etc.) — check --exclude and the defaults.
  • Routes are registered through an indirection the analyzer doesn't follow (a wrapper function several layers removed from the route-registration call).
  • Run with -v to see exactly what the analyzer read and which framework it picked.

"Multiple frameworks detected in go.mod"

Your go.mod imports more than one supported framework (e.g. migrating from Gin to Echo). Pass --framework explicitly to disambiguate.

"This project does not currently pass go vet ./..."

Advisory only — docs are still generated from whatever the AST parser can recover. Run with -v for details on what failed, or pass --skip-build-check to suppress the warning (see Build check).

"N file(s) could not be parsed"

One or more .go files have a syntax error the Go parser can't recover from. Endpoints and types in that file are skipped; everything else still generates. Run with -v to see which files failed and why.

Invalid configuration

Two specific error strings to watch for: an unrecognized type value (only swagger and postman are valid), or an output path that resolves outside your project directory when it wasn't explicitly passed via --output/-o (a deliberate safety check — see Security).

Config file not being read

Ensure .apidoc-gen.yaml is in the directory you're running from, not a subdirectory (or point --config at it explicitly). Inspect the merged result with api-doc-gen generate --show-config.

Prompts appearing in CI

Always pass -y (--no-interactive) and --type. Without these the CLI waits for interactive input. Exit codes in non-interactive mode: 0 success · 1 validation error · 2 runtime error.

Quiet and verbose modes

-q/--quiet suppresses progress output and skips the auto-opened browser preview; errors still print to stderr. -v/--verbose shows the detected framework, endpoint count, matched auth middleware, and per-file parse results.
